# sumi

sumi は、日本語の文章から LLM が生成した雰囲気のある言い回しを機械的に検出し、その修正を支援する単一バイナリのツールである。コマンド名は、炭に脱臭効果があることに由来している。

文章を手で直すだけでは、不自然な言い回しとその修正がいたちごっこになる。そこで sumi は、明らかに不自然で誤検出の可能性が少ない言い回しをパターンとして持ち、linter のように検査して報告する。実装は std クレートのみに依存し、文章の規則は実行バイナリに同梱される。呼び出し側は設定も規則ファイルも渡さず、sumi が持つ規則をそのまま正として扱う。

## インストール

Rust の stable ツールチェーンと Cargo を用意し、次のコマンドを実行する。
開発時の検証には Rust 1.99.1 を使用している。

```sh
git clone https://github.com/hikalium/sumi.git
cd sumi
cargo build --release --offline --locked
./target/release/sumi --help
```

`cargo install --path . --offline --locked` で Cargo のバイナリ用ディレクトリにも配置できる。
実行ファイルを別の場所へ配布するときは [LICENSE](LICENSE) を同梱する。

## 判定の範囲と入力の扱い

sumi は同梱した表現規則との一致を調べる。著者や生成元を特定する判定は対象外である。
検出は推敲の手がかりとして扱い、文脈に応じて事実、必要な条件、不確かさを保って編集する。

文書の検査と結果の出力は、ローカルのファイル操作と標準入出力で完結する。
検出結果には原文の一部が含まれる。出力や文書を LLM サービスや Issue に渡す場合は、
その内容を共有できるか確認する。

## コマンドライン

sumi は、検査対象の文章を標準入力か `--file` で指定したファイルから読み、検査結果を標準出力へと書く。

```
sumi                  # 文書を検査し、違反があれば改善プロンプトに続けて検出結果を出す
sumi --check-only     # 文書を検査し、改善プロンプトを出さずに検出結果だけを出す
sumi --silent, -q     # 文書を検査し、標準出力には何も出さずに終了コードだけを返す
sumi --file PATH      # 標準入力の代わりに PATH のファイルを読んで検査する (-f PATH でもよい)
sumi --lang rust      # Rust のソースとして読み、コメントだけを文書と同じ規則で検査する
sumi --lang html      # HTML として読み、要素の本文と人が読む属性値だけを文書と同じ規則で検査する
sumi --rules          # 同梱の規則の一覧を 1 規則 1 行で出す (avoid -> write | keep | note)
sumi --words          # 語の記録 (登録した語、避ける書き方、一般語と認めた例、標準語と認めた略語) の一覧を出す
sumi --mask           # 各行の各文字について、フェンスか code span なら 1、それ以外なら 0 を並べて出す
sumi install-skill --target codex  # Codex のユーザー用ディレクトリにスキルを配置する
sumi install-skill --path PATH    # 指定したディレクトリにスキルを配置する
```

違反が検出されると、まず LLM エージェントへの改善プロンプト (prompt/rewrite.md と規則の一覧) を出し、「## 検出結果」の見出しの後に検出結果を出す。違反が 0 件なら標準出力を空に保つ。`--check-only` を付けると、プロンプトと見出しを省いて検出結果だけを出す。`--silent` (`-q`) を付けると、標準出力を空に保つ。

ソースコードのコメントも、文書と同じ規則で検査する。`--lang rust` を付けると、入力を Rust のソースとして読み、コメントの外 (コード、文字列リテラル、文字リテラル) を検査から除く。HTML の本文も同じ規則で検査する。`--lang html` を付けると、入力を HTML として読み、要素の中の本文 (SVG の `<text>` の中身を含む) と、属性 `aria-label`、`title`、`alt` の値だけを検査する。タグそのもの、その他の属性値、コメント、文字参照 (`&lt;` など)、`<style>`、`<script>`、`<code>`、`<pre>` の中身は検査から除く。どちらの場合も、検出結果の LINE と COL は元のソースの位置を指す。`--lang` を指定しない場合、`--file` のファイルは名前から言語を推定し (`.md` と `.markdown` は文書、`.rs` は Rust、`.html` と `.htm` は HTML)、推定できなければ Markdown として読む。言語を推定できないファイルで検出が 1 件以上あった場合だけ、Markdown として読んだことを検出結果の前に英語の注意 (`note: ...`) として出す (`--check-only` と `--silent` では標準エラー出力へ出す)。標準入力は文書 (Markdown) として読む。`--file`、`--lang`、`--check-only`、`--silent` は組み合わせて使える。

検出結果は 1 件ごとに `LINE:COL: 「避ける書き方」-> 修正提案` の形で 1 行に出る。LINE と COL は 1 始まりで、COL は Rust における char の単位で数える。`->` の右側は、書き直しを行う人や LLM への提案を自然言語で書いたものである。文脈に合わせて文章を組み直すために使う。

語の規則のほかに、日本語と英語の混在も検出する。1 つの単位 (段落、箇条書きの 1 項目、表のセル、見出し、ひと続きのコメント、HTML のブロック要素) の中に、日本語の文と、機能語を含む英語の語の 5 語以上の並びがあると、その並びの先頭を `LINE:COL: 「英語の並び」-> 単位 (...) を周りの文書の言語 1 つで書き直す` の形で出す。インラインコード、フェンス、「」や二重引用符の中の引用、リンクの行き先、URL の英語を集計から除く。判定の条件と、その値を選んだ理由は [DESIGN.md](DESIGN.md) にある。

操作者が指定した否定構文「〜や〜はしていない」「〜には〜ない」「〜であり〜ではない」「〜という〜ではない」「〜は〜ない」も禁止規則として検出する。丁寧形も対象に含め、事実・現在の状態・対象・次の行動を直接書くよう促す。引用、インラインコード、フェンスなどの除外と、段落などの単位は混在検査と共有する。語の一部として現れる文字列と肯定の形容詞を区別する条件は [DESIGN.md](DESIGN.md) に記録している。

終了コードは、違反が検出されなければ 0、検出された場合は 1 となる。入力が UTF-8 でない、引数が不正であるなどの理由で検査中にエラーが発生した場合は 2 を返す。

## 使い方

典型的な使い方は、次の 3 つの手順の繰り返しである。

1. `sumi < doc.md` で文書を検査し、検出結果を得る。
2. sumi の出力 (改善プロンプトと検出結果) と文書を LLM エージェントへ渡して書き直させる。
3. 書き直された文書をもう一度 `sumi` で検査し、検出結果が無くなるまで繰り返す。

sumi は検出と修正指示の提示を担当し、文章の修正を LLM エージェントに任せる。語を機械的に置き換えると文脈が考慮されず、置き換えた後の文がかえって不自然になるためである。エージェントは、規則の側が誤っている (誤検出である) と判断したら本文を保ち、規則の修正案として報告する。

## Codex スキルとして使う

リポジトリで次のコマンドを実行すると、ビルドした sumi とスキル本文を
`$HOME/.agents/skills/sumi` にインストールする。

```sh
cargo build --release --offline --locked
./target/release/sumi install-skill --target codex
```

配置先には `SKILL.md`、`LICENSE`、コンパイル済みの `sumi` (Windows では `sumi.exe`) を直接置く。
スキルは読み込んだ `SKILL.md` の場所から同梱バイナリの絶対パスを求めて呼び出す。
インストール後の実行に必要な規則と改善プロンプトは、そのバイナリに含まれる。
バイナリはビルドした OS・CPU 向けである。

Codex では `$sumi` を指定し、例えば「この文書を検査して修正して」と依頼する。
検査だけの依頼では検出結果を報告し、修正の依頼では意味と事実を保って書き直して再検査する。

配置先を直接指定する場合は次の形式を使う。`PATH` は `SKILL.md` と実行ファイルを置く
ディレクトリそのものを指し、相対パスは実行時の作業ディレクトリを基準にする。
名前が `-` で始まるディレクトリは `./-name` のように指定する。

```sh
./target/release/sumi install-skill --path .agents/skills/sumi
```

`--target` と `--path` は、いずれか 1 つを指定する。対応する対象名は `codex` である。
`--target codex` は `HOME` の設定を使い、未設定か空なら配置先の明示を求める。
`--path` は `HOME` の設定によらず動作する。

配置先が既に存在する場合はエラーを返し、内容を保つ。更新するときは、既存のスキルを
退避または削除してから、新しくビルドした sumi で同じコマンドを実行する。
成功時は配置先を標準出力に表示して 0 を返し、エラー時は標準エラー出力に理由を表示して 2 を返す。

## 過剰な留保の見直し

「は未実施」「は未検証」「は未確認」「は未確定」(「も」の形を含む) と、
「別途検証する必要がある」「別途確認する必要がある」を検出する。
文末の「が必要になる。」「に限る。」と丁寧形も検出し、必要なもの・対象・条件を具体的に書くよう促す。
「と決めつけない」「と決めつけません」「取り違えに注意」も検出し、対象と確認手順を具体的に書くよう促す。
これらは文脈を読み直すシグナルである。確認した事実と対象範囲を示し、結論と関係の薄い
未実施事項や重複する留保を省くよう促す。必要な不確かさ、注意点、公開範囲は保つ。
これらと否定構文の変更提案には、文が文章の目的に照らして必須かを判断し、
不要なら削除も検討する指示を加える。`--check-only` と `--rules` にも同じ指示を出す。

文章例を編集するときの判断は [アンチケースの説明](anti-cases/README.md) に記載する。

## 規則の足し方

語句の規則は src/rules.rs に静的な表として定義されている。1 つの規則は、avoid (避ける書き方)、write (代わりに書く表現の案)、keep (avoid と同じ文字列を含むが、別の語として許す書き方)、note (避ける理由)、bad (検出する例文)、good (保持する例文) から成る。パターンを文字列そのままで照合する。

語句の禁止規則は次の手順で追加する。留保のシグナルは文脈に応じた見直しを促す規則として扱い、
必要な制約を保つ指示と、原文・改善例の対で検証する。

1. 候補の文字列を、なるべく狭い形で決める。
2. 対象の文書群を grep などで検索し、検出された箇所を全て読む。
3. 誤検出 (自然な日本語が検出されたもの) が 0 件であることを検証する。誤検出があれば、候補を狭めるか、その語を keep に加える。正しい検出があれば、規則を追加した時点で検査が失敗しないように、先に既存の文書を直してから規則を追加する。
4. src/rules.rs に規則を追加する。bad と good は必ず書き、good には keep の語、「」による引用、インラインコードを含む例を入れる。`cargo test` で、bad が検出され、good が検出されないことを検証する。

規則が誤検出を出したら、規則を直すか削除する。各検査を常に適用し、規則の精度を保つ。候補を LLM に集めさせてもよい。その採用条件は [DESIGN.md](DESIGN.md) にある。
